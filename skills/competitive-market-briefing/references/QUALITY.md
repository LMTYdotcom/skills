# Output Quality Standard

Every LMTY-authored PMM skill should produce work that a strong PMM could use immediately.

## Standard qualities

### Decision useful

The output should help someone make, prepare for, communicate, or execute a decision.

Do not stop at a research dump when the skill's job is downstream of research.

### Compressed

Prioritize what matters. The existence of more source material is not a reason to include it.

### Specific

Prefer exact competitor, plan, feature, segment, claim, date, evidence, and implication over generic language.

### Honest

Expose uncertainty and missing context. Do not make the output weaker by pretending to know more.

### Audience aware

A board brief, sales battlecard, and launch readiness review should not read like the same artifact with different headings.

### Reusable

Default outputs should be easy to paste into docs, Slack, decks, launch plans, or other work products.

## Recommended output anatomy

Most outputs should contain some subset of:
- executive answer or TLDR
- what changed or what is true now
- why it matters for the stated job
- evidence and freshness
- gaps, risks, or unresolved questions
- action options or next steps
- appendix or source table when necessary

## What holds in any layout

The user's own preferences can reshape an answer: lead with the answer, shorter, a table instead of prose, options at the end. Follow them. They change the layout, not the evidence. In whatever layout the answer takes, these stay:

- each statement's source and its date, worded by how the date is known
- its grade, where the record gives one
- who said it: the company itself, a named third party, or one person's post
- the line that says how much was read
- the wording rules for what was not found

A preference for opinions, options or a contrarian view does not make room for a claim the record does not hold. A reading of your own is marked as yours, apart from what the record says.

**Count what was read from the calls made.** In "read N of M", N is what the calls returned, counted page by page, and M is the total the tool gave. Before sending, check the line against the calls: a list read to 30 of its 32 entries is "30 of 32", never "32 of 32". Where the source collects nothing for the subject there is no N, and no read line with a zero: say it is not collected, in the skill's words, never "0 posts read" or "read 0".

**Reads from earlier requests in the same conversation count.** What a call returned for an earlier request in this conversation may be used again, and the read line says so: "12 change records read in this conversation, 4 in this run". Read again what may have changed since, and anything the earlier read did not reach the end of.

**A section about what is missing lists the gaps and stops.** "What it leaves out", "Not observed", "Not read", "Could not confirm": each line names what is absent and where it was looked for. No reading of the gap: not "a marketing number", not "regulated buyers are absent", not what the silence suggests. An absence is not a finding about the subject.

**Hold the length the skill sets.** A skill that says one page means one page. Cut the least useful rows before adding a second page, and say what was cut.

## Artifact discipline

When the user asks for a finished reusable artifact, produce the artifact, not a lecture about how to make one.

## Hand-offs

When a request also asks for a sibling skill's job (a price history inside an event prep, a claim verdict inside a customer map, a battlecard inside a prospect stack), name the sibling in one line and do not do its job in this answer: no table, no verdict, no partial version.

## Delivery

Return the artifact in the reply, in full. Then offer to save it.

Do not write a file unless the user asked for one. A skill that silently writes `battlecard-vs-competitor.md` and replies with a summary has taken a decision that was not its to take: the user cannot see what they are about to circulate, and the file lands wherever the agent happened to be.

- default: the whole artifact inline, followed by one line offering to save it
- asked for a file: write it, then say the path and what is in it
- artifact too long to be readable inline: still lead with the artifact, and put the deep evidence in an appendix section rather than moving the whole thing to disk

Never reply with only highlights of an artifact the user cannot see.

## Repeat runs

Each skill says under "Cadence" how often it is worth running. A run is a repeat when the user says so, when it is a scheduled task, or when an earlier output of the same skill is in the conversation, in memory the client itself provides, or in a file or channel the user points to. Do not search files or folders for one.

On a repeat run:

- lead with what is new since the last run, and give the date of the run you are comparing against
- match items by what identifies them: a source's address and date, an event's id. A report change has no id: match it by its subject, its title and the date it was recorded. In an audit or a refresh, an item is a claim and the asset it sits in. Skip what the earlier run already reported, unless it changed
- when nothing is new, say "nothing new since [date]" in one line and stop. A short report is the correct report
- keep the same sections in the same order, so two runs can be read side by side
- never claim to remember an earlier run you cannot see. With no earlier output to hand, say that this run is the baseline. A scheduled run that cannot see its earlier output covers the period its schedule implies (the last seven days for a weekly run) and says so, instead of calling itself a baseline every time

## Destinations

The reply is the default destination. When the user names another one and a connector for it is available - a team chat channel, an issue tracker, a document, a file - deliver there as well:

- fit the form to the place: in a chat channel, the takeaway and the three or four items that matter, then where the full version is; in an issue tracker, one issue per item someone must act on
- say what was sent where
- show the list before creating more than five items anywhere
- when the connector is not available, say so and return the artifact in the reply

**Anything addressed to someone outside the user's organization is a draft.** A reply to a post, a public correction, a message to a prospect or a customer: write it, mark it as a draft for a person to review and send, and send nothing. This holds even when a connector could post it.

## Comparison discipline

Avoid feature-table theater.

A comparison should emphasize:
- dimensions customers actually evaluate
- meaningful parity and difference
- who cares about each difference
- evidence
- where the home product is weaker

## Recommendation discipline

A useful PMM recommendation connects:

**market evidence + customer/deal evidence + company strategy + timing**

If one or more inputs are unavailable, reduce the strength of the recommendation rather than hiding the gap.
